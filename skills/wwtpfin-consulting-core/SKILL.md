# wwtp-fin Consulting Core

Use this CLI when the task needs deterministic wastewater-project financial calculation, checks, evidence-aware findings, structured report content, tables, or figure briefs. Do not use it to write an unconstrained narrative, make a Word file, draw a chart, infer missing facts, or replace an engineering/design study.

The business user supplies materials, goals and feedback. In one continuing case, take responsibility for investigating measures, testing important assumptions and giving a supported recommendation before asking for a scheme choice. Internal iterations are part of that service; do not depend on an expert user or another fresh session to discover missing alternatives. A recommendation is bounded by the evidence, modeled scope and tested scenarios, never a claim of an absolute best plan across all possible measures.

## Project workspace

The user supplies materials, not folders. Before conversion, create or reuse one case directory and place files according to [workspace management](references/workspace.md). Copy source files into `sources/`; never move, rename, edit, or delete the user's originals.

Use the same-version package skill assets; a machine-global copy may be stale even when the skill name matches.

Maintain one editable input set under `input/`. Every accepted input revision gets a numbered run containing an input snapshot and the CLI deliverable. A run becomes immutable after quality and deliverable verification pass. Downstream exports must be bound to the exact verified run that produced them. After selection, put presentation-only explanations and export scripts under `exports/run-NNNN/`, not the bound `input/` tree; follow the workspace reference when a genuine input change requires renewed research.

## Workflow

Resolve the tool's asset root before reading `docs/` or `examples/`: use the source repository when working there, otherwise locate `@dztabel/wwtpfin` under `npm root -g` (or the active local npm installation). These paths are relative to that asset root, not the case directory. Compare its `package.json` version with `wwtp-fin --version`; update mismatched CLI and skill assets before using new commands. The installed CLI schemas remain authoritative.

1. Create or resume the case workspace. Copy the supplied Word, Excel, PDF and other source files into `sources/` while preserving their names.
2. Read `wwtp-fin --help`, the current input and evidence schemas, `docs/INTAKE.md`, and `examples/minimal_complete/`.
3. Convert `sources/` into `input/project-draft.yaml`, `input/evidence.json`, and `input/conversion-log.md`. Preserve source wording, locator, date and evidence state, including qualifications that change meaning: annual average versus peak/design capacity, project scope, units, time period and tax basis. Complete the source-to-field ledger, conflict ledger and conversion-completeness matrix before continuing.
4. Run `wwtp-fin intake -p input/project-draft.yaml -o input/intake-advice.json` after recording the disposition of material source items. Keep conflicting facts unresolved. Missing workbooks do not prevent authorized, source-backed estimates or conditional scenarios: record the method, source, uncertainty and intended use; do not represent an estimate as a fact. Ask one prioritized batch only for information that actually blocks useful work. Product defaults remain proposals, not evidence.
5. Establish a calculable working baseline as `input/project.yaml`. Reproduce a source-declared baseline when the materials contain one; otherwise, within the user's research authorization, combine sourced facts, supported estimates and explicit design proposals into a conditional baseline. Preserve missing source facts in the conversion ledger and label every proposal; a complete historical source model is not a prerequisite to research. Diagnose the result before comparing changes; a baseline is not a best plan.
6. Read the completed input’s `intake.research_plan` for required basis paths and concrete study subjects. In a complete decision, bind facts, estimates and design choices to current values and sources through `parameter_basis`; estimates also bind uncertainty and the actual scenario values. Read `research_review.plan_review` after comparison for newly introduced candidate/continuation subjects. Studying one cost item does not cover another, and `material: false` never waives scenario testing. For iteration, follow [modeling and iteration](references/modeling-iteration.md). Establish a separate decision contract with `cost_goal`, explicit primary and, where needed, secondary objectives. Explain the cost perspective in the user's terms: total construction and operating cost is not automatically fiscal expenditure or a narrower investment/opex subtotal. Actively research applicable engineering, operations, policy, financing and delivery alternatives. Maintain `research` in the scheme set, calculate complete combinations and common assumption scenarios, and read both `decision_review` and `research_review` before recommending a choice. An incomplete review requires further work; a ranking reversal requires a conditional recommendation, not a hidden choice of favorable assumptions. Distinguish numerical feasibility, recommendation support and implementation readiness. Before recommending, challenge the exclusions that most influence the choice against the full source provision or complete counterfactual calculation. A conclusion must not exceed its source or tested scope. If no source-backed measure exists, record the research and the evidence needed to continue rather than manufacture an alternative.
7. For a baseline or conditional `build`, create the next `runs/run-NNNN/`, copy its working input snapshot and build into an empty `deliverable/`. For a selected `finalize`, supply a new empty run path; that command creates its own bound snapshot.
8. Inspect every `warnings.json` item and `quality.json`, then run `verify-deliverable`. Read `document.json` / `report.md`, `result.json`, checks, decisions, tables and figure briefs together; never promote a warning, missing input, or unverified benchmark into a conclusion.
9. After an explicit scheme choice and completed cost-goal and research reviews, distinguish selection of conditional research assumptions from implementation-condition readiness using `selection_scope`; preserve pending conditions in a conditional study. A user may choose an assumption-dependent tradeoff, but confirmation does not turn it into a robust winner or bypass cash deficits, bad references or incomplete research. Use `finalize` to generate a new complete run and `verify-final-run` to validate its binding. If the choice has continuation service, retain its separate complete deliverable and the common-period cost ledger in that same run. Never select a final scheme by run number or modification time. For a standalone calculation, identify it as baseline or conditional work. Produce Word or rendered charts only when requested, using the explicitly selected verified run and [downstream handoff](references/handoff.md).

Read each candidate's `model_eligibility` for the original contract, continuation and common scenarios. Known scope gaps require a modeled remedy; explicit policy contradictions remain counterfactuals. Missing eligibility evidence produces specific pending policy conditions and permits conditional research. Resolve those findings through the corresponding model evidence and recompute; a generic approval or editing an automatic condition cannot clear them.

```bash
wwtp-fin schema --kind input
wwtp-fin schema --kind project-evidence
wwtp-fin schema --kind scheme-set
wwtp-fin schema --kind decision-contract
wwtp-fin schema --kind scheme-selection
wwtp-fin intake -p input/project-draft.yaml -o input/intake-advice.json
wwtp-fin compare -p input/project.yaml --contract input/decision-contract.yaml --evidence input/evidence.json --schemes comparisons/compare-0001/scheme-set.yaml -o comparisons/compare-0001/output
wwtp-fin build -p runs/run-0001/input/project.yaml --evidence runs/run-0001/input/evidence.json -o runs/run-0001/deliverable
wwtp-fin verify-deliverable runs/run-0001/deliverable
```

## Current work and return paths

For interactive cases, use package `docs/CASE_WORKFLOW.md`. Record each user request verbatim and the business response with reasons; `case checkpoint` stores the input/evidence snapshot and current artifact. At receipt of a material change, record work in progress before further research, so an old recommendation is not presented as current. At every response, resumed session and export, run `case status` and direct the user to `CURRENT.md` plus the exact artifact. Return to any earlier stage when new facts or preferences require it; preserve old rounds and selections.

Record a comparison with its actual scheme-set path, not just the result JSON. Record the selected final run after verification. `current` means consistent with current inputs, not approved or optimal. A stale or in-progress state must not fall back to a historical result. Before exporting a selected scheme, use `verify-final-run RUN --case CASE`; historical file integrity alone cannot establish current validity.

## Required conversion discipline

- Preserve missing financing as unresolved in the source baseline. With authorization to explore alternatives, use explicitly proposed loan scenarios with recorded sources or estimation methods; these are not commitments, approval or confirmed terms.
- The source-declared baseline may reproduce explicit terms and assumptions that the supplied scheme actually uses, even when their evidence state is `proposed_not_binding`. Preserve that state and say the run reproduces the source scheme; never call those terms binding, verified, recommended or optimal. Other proposals stay unresolved in the source-faithful draft, but may enter a separately identified, authorized conditional research baseline or candidate.
- For explicit `opex_items[].annual_amounts_wan`, do not invent formula-only `base_wan`, `scales_with_volume` or `annual_growth_rate`. `price_adj_group` is required only when tariff adjustment is active; `vat_scope` is required only when by-product revenue exists.
- A spreadsheet formula is usable only after its references, cached result, units and labels agree. Record any contradiction as unresolved; never infer financing terms from schedule shape.
- Conversion is incomplete until calculation fields and source material on risk allocation, performance supervision, termination and transfer are each mapped, unresolved or explicitly not applicable.
- For any nonzero or modeled terminal value, explicitly distinguish the valuation method from the asset event. Use `terminal_asset_event: continued_use` when assets remain in use: their evaluation residual is not sale proceeds, spendable reserves or a refund to the government. Use `disposal` only for a stated disposal/transfer assumption with its basis. Complete input requires the event whenever terminal value is enabled. Read `TERMINAL_CASH_RECOVERY` and the verified cash tables for actual cash; never copy an appraisal or book value into payer inflows.
- Never invent project facts or derive tax eligibility from a favorable result. Distinguish fact, design choice, estimate, negotiation proposal and missing information. Supported assumptions may be calculated within an authorized exploration; final decisions must disclose their conditions. A product default is a labeled proposal, not a fact.
- In complete decision research, each fact, estimate and design choice needs a `parameter_basis` supporting record binding its kind, current resolved baseline values, derivation method and source references. Facts require reproduced source snapshots; estimates require supporting workpapers and the documented scenario values. A forecast remains an estimate even when printed in a source report. Never change `kind` merely to avoid scenario testing. See [modeling and iteration](references/modeling-iteration.md) for the binding and effective-change rules.
- Create external source snapshots with `source-snapshot` from saved originals, using the exact extracted text and artifact descriptor. Complete research checks the original bytes and repeats the extraction; a self-written summary with a valid hash is insufficient. See [conversion discipline](references/conversion-discipline.md) for locating and archiving excerpts. Review table headings, units and parent/subset relationships separately: faithful extraction does not certify their interpretation.
- Numeric estimates also need the CLI-checked `parameter_basis.derivation`: located source values and units, formulas, and output parameter paths for the baseline and common scenarios. Read `estimate_derivation_review`; do not use a prose workpaper when its numeric derivation disagrees with the actual input. The arithmetic check does not establish that the estimation method or range is appropriate.
- Use the generated `decision-brief.md/json` as the numerical source for a recommendation and the selected-run version after `finalize`. It preserves goal order, conditional branches, ties, money valuation and period labels. Explain it in business language without re-ranking by a secondary metric or relabeling present values as nominal amounts; a different client tradeoff remains separate from the computed recommendation.
- Bind each structural exclusion and `user_bound` claim to the actual quoted source scope. Keep `scope.contract_values` (common horizon and comparison rules) separate from `scope.parameter_values` (explicit user-fixed leaves). A common service horizon does not fix the concession term, continuation or terminal arrangement. Ordinary contract locks do not prove a user instruction or exempt inputs from classification; follow `scope_constraints_review` and the source-scope details in `docs/RESEARCH_REVIEW.md`.
- `intake.ready=false` describes the current draft, not a ban on designing research scenarios. For example, an unset service price may be a variable to solve, and an undecided financing arrangement may be a proposal to compare. Explain the proposed objective, bounds and assumptions; do not require an existing priced financial workbook before iterating. If the requested scope truly cannot be represented, record the specific missing capability. External scripts may convert engineering quantities into inputs and independently cross-check results; they must not replace the CLI financial calculation or be presented as its completed workflow.
- Do not elevate evidence state, turn a table into prose, serialize raw JSON into the report, or use a shared rule catalog as project evidence.
- Record full material qualifications in `declared_basis`; retain declared totals and targets in `declared_scalars`.
- Conflicting total-investment declarations remain unresolved regardless of source order. Read `D7-10`, the full reconciliation and separately labeled computed total; do not use the first declaration to derive a support ratio or make a definitive source claim.
- Keep pre-tax, after-tax and target bases distinct. A financial benchmark must record its source, date, provider and evidence state.
- Handle `profit_distribution_policy` as one group. If a source policy or user choice is truly required, ask once; within authorized research, propose and explain a legally supportable allocation scenario. Never use 0 or 100% merely to fill a missing fact; an explicit research proposal at either endpoint must state its purpose and consequences, without claiming a company resolution.
- When a binding source gives cumulative water thresholds and tariff multipliers, map them to `revenue.marginal_volume_tiers`; the last tier has `up_to_m3d: null`. In source reproduction, proposed clauses enter only if the source actually applies them. Authorized alternative clauses may enter separately labelled conditional candidates with explicit thresholds, rationale and conditions; never call them existing contract terms.
- Review `D7-*` warnings individually. A successful exit code does not erase a warning.

Read [conversion discipline](references/conversion-discipline.md) before material conversion.

## Read the result correctly

- `decision_review` checks the structured cost goal, service/compliance/return requirements and evidence references. New selected runs require `cost_goal`; the primary metric is `decision_cost_wan` or `decision_cost_npv_wan`, minimized in 万元. Actual service and compliance requirements must be linked to implementation conditions; a required investor return needs a real return/NPV lower bound. Do not copy an example's return requirement into an inapplicable mode. Actual cumulative cash gaps, model gaps and explicit contractual ratios still block selection. A cash DSCR below 1 alone does not: where cumulative cash closes, inspect `financing_review` and its required cash-availability condition before a conditional study or implementation selection. See package `docs/COST_PERSPECTIVES.md` for the four perspectives and complete contract.
- A comparison's `research_review` reports the declared research coverage and actual scenario results. Inspect unresolved issues, tied winners and whether one candidate remains preferred across the tested scenarios. Passing this review checks the recorded finite comparison; it does not validate source interpretation, exhaust engineering alternatives or certify policy eligibility. Use package `docs/RESEARCH_REVIEW.md` for the input contract and status meanings.
- Effective research changes must affect modeled inputs. Renaming a project or changing source/display metadata cannot count as a measure, scenario or combination; changing a real financial parameter can count even when the current output remains zero. Preserve full input/currentness binding separately from this research check.
- Different contract lengths currently compare only through `payer_net_outflow`, with the same project start/commissioning, equivalent timed service and a common horizon. Short contracts, including the base, need fully calculated continuation models and common scenario coverage; do not truncate a long contract, fill missing service with zero, or extrapolate an average annual fee. Do not switch the user's cost perspective merely to fit this capability. Read the period-comparison section of `docs/COST_PERSPECTIVES.md` before constructing such candidates.
- `quality.json`: whether the completed content package passed its quality gate.
- `warnings.json`: input-shape information requiring correction, an explicit limitation, or an unresolved registration.
- `result.json`: calculation, checks, analysis, decisions, evidence and downstream data.
- `tables/cash_funding_summary.csv` and `cash_funding_components.csv`: complete period-by-period cash sources and uses, including construction, operating capital contributions, loans, grants, renewals and distributions. Use these verified tables for funding explanations; distinguish cash receipts from revenue and cash payments from costs. Trace a funding-gap amount and period to the closing-balance series and the input assumptions that created the relevant spending. A calculated deficit is conditional on those assumptions, not proof that an estimated renewal date or amount is established.
- `document.json`: complete authoritative machine semantics for downstream selection.
- `report.md`: deterministic financial consulting core only: calculation basis, key metrics, financial analysis, decisions, risks and required inputs. It is not a complete project report.

## Final response

State the selected run number, result summary, and output paths. Explain why the recommended or selected plan is suitable, the evaluated alternatives, and any assumption that changes that judgement. Name the cost perspective, service period and baseline source beside any saving claim; an agent-estimated baseline is not a source document's declared total. Keep each financial/cash conclusion attached to the account and assumptions it actually evaluates; a separate fiscal spending plan is not proof of funded project cash. List every remaining input warning and material unresolved limitation, even when build, quality, charts, and Word QA pass. Never let “build passed” imply that project evidence or input assumptions are complete.

For command exit meanings and output contract, use `docs/contract-surface.md`. For current implementation limits, use `docs/boundary.md`; do not present probability/Monte Carlo analysis or a complete statutory VfM study as available. Operating-period debt is limited to loans bound to same-year capital assets; mixed-use long-term-asset VAT requires an explicit tax-workpaper schedule.
