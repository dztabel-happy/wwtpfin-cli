# Modeling, measures and selected results

## Stage 1: establish the starting point

Create `input/modeling-decisions.md`. Separate source facts and mandatory rules, design choices, negotiable arrangements, bounded estimates/scenarios and missing information. Record the source locator, evidence state, current value, supported alternatives and decision owner. A preliminary study is a starting point; its proposed numbers are not automatically fixed facts.

When the materials contain a source calculation, retain it as `baseline_status=source_declared_baseline`. If there is no complete source model, create an authorized conditional research baseline from known facts, supported estimates and proposed design choices. Preserve the source gaps; do not require a nonexistent source model to run first. Any estimate or correction changes the basis and requires a new, clearly labelled run.

Create `input/decision-contract.yaml` using `wwtp-fin schema --kind decision-contract`. Use its `cost_goal` to record the actual goal and evidence, one of four cost perspectives, `valuation`, the common `horizon_years` including construction, `discount_rate`, and requirements. For nominal cost the primary objective is `decision_cost_wan`; for present value it is `decision_cost_npv_wan`; both use `direction: min` and `comparison_basis.unit: 万元`. Free-text scope cannot redefine the machine metric. If more than one outcome matters, distinguish the primary objective from ordered `secondary_objectives`; a secondary objective breaks primary-objective ties within the stated absolute `tolerance`. It does not justify silently switching the main objective. Record numeric hard constraints and fixed parameter paths using canonical `Params` values, plus required implementation conditions and responsible parties. Missing `cost_goal` can support exploration, but cannot produce a new selected result.

Classify all three `cost_goal.requirements`: `service`, `compliance`, `investment_return`. Each has `status`, `constraint_metrics`, `condition_ids`, `basis` and nonempty `evidence_refs`. Service and compliance must be `required` and reference real contract conditions. A required return must reference an actual return/NPV lower bound in `hard_constraints`; cash balance or equity share is not investor return. Use `not_applicable` for return only when justified for this decision, with evidence; do not copy a concession return target into an unrelated mode or suppress a real investor's required return. All references must resolve to the bound supporting records. Mechanical reference validation does not prove the classification or the source meaning.

For “total construction and operating cost”, explain a suitable project cost perspective, usually `project_cash_cost_net` when financing, cash taxes and working capital belong in the requested scope. It does not subtract operating revenue or grants. Use the narrower `investment_opex_outlay` only with its exclusions clear; use `service_grant_payment` for contractual payments and `payer_net_outflow` for an explicitly scoped party's net outflow. Do not silently replace project cost with fiscal burden, equate a starting tariff with total cost, or add overlapping perspectives. Read package `docs/COST_PERSPECTIVES.md`. If the exact requested scope is unsupported, document the missing mechanism; a separately verified workpaper can explain a bound, but is not a completed CLI comparison or selected deliverable. Never relabel a different metric to bypass that limitation.

Do not require all decisions before useful work can begin. Within an authorized exploration, construct transparent estimates from engineering quantities, applicable quotas, regional prices, quotations or explicit proposal ranges. Record region, edition/date, units, taxes, uncertainty and replacement evidence. Distinguish uncertainty in an amount from uncertainty in the method that generated it. An arbitrary percentage around one method does not test a competing plausible method. Missing workbooks need not block this work. Keep missing facts unresolved; do not infer lending commitments or tax eligibility.

## Stage 2: discover measures, calculate and improve combinations

Diagnose the baseline, then connect every proposed measure through:

**Effective source → project applicability → real action → linked parameter changes → financial impact → cost/responsibility/implementation conditions.**

Sources can be policy, contract alternatives, engineering studies, quotations or cost estimates. A numerical sensitivity boundary does not prove a measure achievable. Policy existence does not prove project eligibility. An open measure register is a working aid, not a finite product capability list.

Research proactively before handing the user a selection menu. The user should not have to supply policy names, spot inconsistencies or request the missing financing variant. Check applicable primary sources for current policy terms and effective dates; use engineering evidence, local prices and quotations where they govern the action. A draft's assumptions are neither binding restrictions nor permission to use any cheaper number.

Maintain the scheme set's `research` object using the installed schema and package `docs/RESEARCH_REVIEW.md`. The six directions are coverage questions, not a demand for six candidates: service/demand; capital/renewal; operations; tax/support; financing/payment; delivery/contract. Assess each applicable direction, preserve the evidence for an exclusion, and keep unresolved promising work open. A financing or payment change cannot be dismissed merely because it leaves resource cost unchanged if it affects a declared secondary objective, feasibility, timing or risk that will influence the recommendation. If that outcome is not yet in the decision contract, explain the tradeoff and revise the contract before using it to rank plans.

Record the canonical paths affected by measures and influential assumptions. For each assumption distinguish `source_fact`, `estimate` and `design_choice`, explain its basis and evidence, mark its materiality, and link actual scenarios. A source fact must preserve its qualification and scope; a working estimate cannot be reclassified to avoid scenario testing. `user_bound: true` is reserved for a design choice the user actually fixed, with the confirming reference. The agent's own default, the first proposed value, or the user's general goal does not make it user-bound.

- **Representable:** build a supported scenario and calculate it.
- **Needs upstream calculation:** calculate the engineering/tax workpaper with sources before mapping the result.
- **Approximation or bound:** explain what the calculation can decide and what it cannot; retain pending conditions.
- **Unrepresentable:** register the exact unsupported mechanism and affected results; do not imitate it with a different cash flow.

Use `sensitivity` and `solve` to identify influential variables and boundaries. `solve` currently supports transfer consideration, blended tariff and operating duration (a month grid when time_basis is provided); other choices use explicitly constructed scenarios. A price that meets a return threshold does not determine which engineering or financing plan is preferable. CLI does not automatically select a plan or establish a “best” scheme.

Do not request permission again for individual trials within already authorized exploration. Present concrete choices after calculating them. If no source-backed alternative exists, record `no_source_backed_candidates` and investigate or request the missing evidence rather than inventing a candidate.

For every comparison, pass the same decision contract and exact evidence snapshot. The contract's hard constraints are inherited even if absent from the scheme set. Changing the objective or fixed boundary requires revising the contract and restarting comparison on that basis. Condition entries use `pending`, `satisfied` or `not_applicable`; satisfied/not-applicable entries require actual references and an explanation, not a trial result. Their status is a responsible-party declaration, not independent CLI legal/technical certification.

Read the complete constraints, fixed-parameter changes, comparability, `model_limits` and conditions, not only `shortlist`. `numerically_feasible` covers numerical and fixed-boundary checks; `feasible` also requires comparable cost/payment scope. `selectable_shortlist` additionally requires no unresolved model limits and recorded implementation conditions. `research_selectable_shortlist` permits a user to confirm research assumptions while implementation conditions remain pending; it still requires a bound contract, numerical/fixed-boundary and comparability checks, and no unresolved model limits. A successful command or complete deliverable is not project approval. An empty implementation shortlist can therefore still support an explicitly selected conditional study; an empty research shortlist requires further modeling or iteration. Read `decision_review`: missing goal/requirement references prevent finalization; bad satisfied/not-applicable condition or payer-cashflow references remove candidate eligibility. Scenario payer receipts and expenses are checked too, so changing a scenario cannot introduce unregistered funding and retain a recommendation.

These candidate eligibility fields do not prove the research is ready for selection. Read `research_review.ready_for_selection` and `decision_review.passed` separately. The candidate lists and research scenarios use the same ordered objectives and tolerances. Read the full `best_candidates` and `ranking_groups`; IDs inside a tied group are display order, not preference. `best_by_objective` is null when the first group is tied. None of these single-case rankings certifies a recommendation. An absent or incomplete review cannot be repaired by asking the user to select the apparent cheapest candidate.

Every research `evidence_refs` entry must resolve to a unique supporting record in the bound evidence, including estimates, scenarios and calculated combinations. Register the real workpaper or material before citing its ID; a typed URL or invented ID alone is not registered evidence. Ordinary estimates may remain `unverified`; only structural exclusions require full source snapshots. When a user actually fixes a design choice, record its paths and values in the decision contract as well as its reference before setting `user_bound`; an agent-proposed default is not a user-fixed boundary.

Use `docs/FUNDING_STRUCTURE.md` to declare construction-grant allocation, debt/equity bases and engineering-backed operating-capex purpose. Never infer expansion from a favorable DSCR result. Check all capital outflows and cash gaps even when a DSCR basis excludes expansion. A grant used to reduce borrowing or equity cannot also be counted as shareholder income. Where a minimum equity share applies, constrain `construction_equity_ratio_actual`, not just the proposed input ratio. Classifications, grant use and financing may be conditional proposals; preserve their evidence state. Legacy reproduction with material unresolved funding or investment scope cannot be selected for finalization.

Use `docs/COST_PERSPECTIVES.md` to choose investment/operating outlay, project cash cost, service/grant payments or an explicitly scoped payer net outflow. Keep nominal and present values separate. Missing payer receipts are unknown: use partial coverage and a source-backed conditional scenario, not zero receipts disguised as fiscal net burden. Compare new measures against the same baseline and discount/service scope; an invalid starting-price proxy must be replaced by a complete payment metric. Inspect the per-period ledger and investment VAT basis before interpreting savings.

Keep declared `dscr_min`, cash-generation `cash_dscr_min` and `cum_cash_min` separate. The cash ratio excludes book grant income and new financing, deducts sustaining investment and working-capital injections, and includes all modeled debt service. Under `cost_goal`, CLI automatically requires `cum_cash_min >= 0` and, for an original contract with debt, `cash_dscr_min >= 1`; stricter contract requirements remain. A failed candidate is a useful research result but cannot be selected even for conditional research. Diagnose opening cash, capital outlays, financing and risk margin through `dscr_cash_bridge` and the verified cash tables. Model a supported funding solution and recalculate; a fiscal requirement schedule or a promise to budget later is not cash received by the modeled account. These are product numerical gates, not an automatic lender rejection or approval. Income-tax exclusion of a VAT refund does not remove its accounting income; tax eligibility remains a separate condition.

Recompute each complete combination; never add independent savings as the combination value. A measure not preferred because of its numerical result remains `evaluated`, with a complete counterfactual candidate tested under the common scenarios. A null combination is reserved for a source-supported structural incompatibility, not “too expensive”, “little benefit” or a weak standalone result. For a structural exclusion, supply `exclusion` with its real candidate scope, applicability and relevant exceptions; each `evidence_refs` entry must resolve to a source snapshot in `evidence.supporting`. See `docs/RESEARCH_REVIEW.md` for the exact contract.

Test the full economic effect, including timing, eligibility, resource requirements and funding. A zero balance, refund or amount in one tax or accounting line does not establish zero total benefit: changing its treatment can alter other taxes, asset bases, cash requirements or payment levels. Follow those linked changes through a complete recalculation under the same pricing and comparison rules. A losing standalone candidate is not a lower bound on all its combinations. Do not stop at independent measures when feasible combinations could improve the result.

For a material uncertainty, apply the same scenario interpretation to every candidate. `research.scenarios[].overrides` is applied after each candidate's parameters. If an engineering relationship requires candidate-specific derived quantities, use the scenario's `candidate_overrides` with the recomputation basis; do not use it to give one candidate a favorable independent assumption or overwrite a common scenario value. Recalculate complete quantities and schedules when the assumption changes. Keep scope, taxes, units and objective basis comparable, and examine failure of conditional measures as well as favorable performance. The goal is to expose changes in feasibility and recommendation, not to accumulate a large number of trivial runs.

For different original contract terms, read `docs/COST_PERSPECTIVES.md` before building candidates. This comparison currently supports only `payer_net_outflow`, with identical project start/commissioning, the same payer/scope, equivalent timed service and one common horizon. Keep every original contract cash flow and terminal obligation. A short candidate needs `continuation: {params, basis, evidence_refs}`; a short comparison baseline needs top-level `base_continuation`, even when `include_base` is false. The continuation `params` must be a complete independent input, begin immediately after contract expiry with zero construction duration, and end exactly at the common horizon. Rebuild its service, assets, renewals, taxes, financing and cash schedules; do not extend arrays, fill omitted years with zero, annualize an average fee or assume free asset/cash transfer. Other cost perspectives cannot yet use this unequal-term mechanism; do not change the user's objective just to obtain a comparable result.

Treat continuation as part of the research. Its parameters are exposed under the virtual `continuation` path; use that whole path when adding a continuation to a base that has none, and explain the full arrangement. Every common scenario must provide `continuation_overrides` for all candidates with continuation plus `base` when `base_continuation` exists. Each value has `overrides`, `basis` and nonempty `evidence_refs`; explicitly unchanged entries use `{}` with a reason, not omission. Changed continuation paths must belong to the linked assumptions. All continuation arrangements, including the comparison base, need effective condition testing; do not keep every entry empty. Apply a shared long-term assumption to both a short contract's continuation and the corresponding years of longer contracts. Both original and continuation discount rates retain the goal's common valuation rate; a loan-rate scenario does not change that ruler. Do not put continuation parameters inside ordinary scenario `overrides`. Exact schema and the research path rules are in `docs/RESEARCH_REVIEW.md`.

The continuation is fully recalculated, must close cash, and with debt must meet both declared and cash DSCR minima of 1. Applicable contract return, cash/debt and equity-share constraints carry over to it. An estimate for future service remains an estimate, not an approved renewed contract. Missing, duplicate or unresolved continuation and scenario payer references block recommendation rather than being accepted because the aggregate total is cheap.

Before closing research, review the six direction dispositions, influential estimates/design choices, unexplained parameter changes, combinations and actual scenario results. As part of the source self-check, challenge the exclusions that most affect the recommendation: does the full provision contain an allowed route or exception, and does a complete counterfactual still support the stated numerical reason? Narrow the conclusion to the actual source and tested scope; reopen it when they do not support the exclusion. This is a targeted review of decisive judgments, not another approval stage. Write a concrete `stopping_reason`: why the evaluated set supports the recommendation, what remains outside it, and what new evidence would reopen it. Do not use “all commands passed”, a fixed number of candidates, or user fatigue as that reason. An open promising direction or untested material assumption requires further work, not another fresh user session. When no feasible candidate remains, identify the controlling constraints and the next useful change or evidence request.

Organize a small set of complete plans for the client, with the common baseline, whole-life effects, financing/cash closure, responsibilities and failure fallback. Explain the recommendation in business terms: why it meets the goal, why alternatives were not preferred, and what could reverse that conclusion. If the same candidate wins within the stated tolerances across tested scenarios, describe it as stable within that tested scope. If rankings reverse, present the calculated branches and the condition that distinguishes them; recommend a conditional choice or an evidence-gathering action. Never hide the reversal by choosing one baseline, silently switching objectives, or averaging incompatible cases. Keep numerical ties as ties unless a recorded secondary objective resolves them. The user retains the choice; the agent retains responsibility for the quality of the analysis offered.

## Stage 3: explicit selection and complete calculation

Keep `decision_status=user_confirmation_required` until a choice is actually made. Only after explicit confirmation and a research review ready for selection, record a selection using `scheme-selection`: exact comparison content hash, candidate ID, canonical parameter hash, confirmation identity/time/reference and purpose. Preserve the reason for the choice and acknowledgement of the research status. A user-selected tradeoff or assumption-dependent candidate must not be described as a robust winner. Record the scope separately: `selection_scope=conditional_research` only when the user explicitly chooses to complete the study under its stated assumptions; keep every pending implementation condition and failure fallback. `selection_scope=implementation` (the default for older records) retains the strict condition gate. Research selection never bypasses numerical, fixed-boundary, comparability, model limits or the research-review gate. Use the bundled [selection-record helper](../scripts/record-selection.py), with `--selection-scope conditional_research` for that explicitly confirmed scope, to bind these values without transcribing hashes. Do not hand-copy rounded prices into the selected input.

`purpose=workflow_validation` is mandatory for synthetic/simulated acceptance; never represent it as a real client decision. `purpose=selected_scheme` records an actual decision. These records bind content; they do not authenticate the human or replace the referenced confirmation.

```bash
wwtp-fin compare -p input/project.yaml --contract input/decision-contract.yaml --evidence input/evidence.json --schemes comparisons/compare-0001/scheme-set.yaml -o comparisons/compare-0001/output
wwtp-fin finalize --comparison comparisons/compare-0001/output/scheme-comparison.json --selection selections/selection-NNNN.json --contract input/decision-contract.yaml --evidence input/evidence.json -o runs/run-NNNN
wwtp-fin verify-final-run runs/run-NNNN
```

`finalize` rechecks the contract including `cost_goal`, evidence, software, full parameters, decision/research reviews, numerical constraints and implementation-condition records under the confirmed selection scope, then runs the complete calculation/build chain. With continuation it produces the original `deliverable/`, separate `continuation-deliverable/`, and common-period `cost-comparison.json` / `cost-cashflows.csv`, all bound by `final-run.json`. Continuation evidence is scoped to its referenced supporting records; it does not inherit original-source declared indicators or decisions. Its `continuation_context` identifies the selected study and requirements, not a separate user selection. Both `CURRENT.md` and the financial core retain the conditional-study scope, pending conditions and simulation label when applicable. Changed inputs, evidence, software or decisions require a new comparison and confirmation. Failed runs remain staging; successful runs are immutable. A report or complete recalculation does not strengthen the recommendation beyond its recorded research scope.

The selected run is the sole financial source for exports. Put explanation generators, rendering scripts and presentation-only workpapers under `exports/run-NNNN/` (for example `scripts/`), not `input/workpapers/`; adding a file to the bound input tree can invalidate its current selection even when no parameter changed. Verify currentness after export. New evidence discovered during report writing that affects a calculation or recommendation returns to modeling/iteration. Never choose the newest trial as the final run. A client can request a report of an explicitly identified baseline or conditional run; clearly label that purpose and preserve its limitations.

## 非整年项目

建设与运营实际期限按原文分别登记，不能向上取整。先读取包内 `docs/TIME_AXIS.md`；声明项目开始月份、期间金额口径和依据，按时间轴的分期数转换数组。开始月份缺失时可登记条件提案并试算，不能标作原始事实。期限改变后须重新核对水量爬坡、设备/融资/拨付事件及显式金额覆盖，不能把旧年度数组当作已转换。确认成果包含实际期间表，并复核总期限、首末期收支和折现时点。

## 推荐方案的剩余措施

读取 comparison 的 `research_review.combination_coverage`。CLI会按每个情景的赢家检查已研究单项是否已包含、已做准确组合或有依据排除；缺失则继续计算。不要依靠业务人员看到菜单后才提醒把两个可兼容措施合并。新组合成为赢家后，继续检查它剩余的措施，直到当前已发现范围内闭合。

组合中的融资等措施被替代时，在 `replaced_candidate_ids` 显式列出旧单项ID。既有组合登记引用旧方案不代表旧方案的全部措施仍然生效。不能用多带一项不利措施的组合、复制原参数或不真实的互斥理由充当测试。CLI检验计算和谱系，专业人员仍负责依据及工程含义。
